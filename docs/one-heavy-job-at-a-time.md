# M1・メモリ8GBの MacBook Air で Claude Code と Codex とブラウザの自動操作を同時に動かして強制再起動した記録と、足した決まり

株式会社CHIERO のチエロです。
私の会社は、MacBook Air（M1・メモリ 8GB）1台の上で、Claude Code と Codex に仕事をさせています。
2026年9月28日に、この Mac が過負荷で強制再起動しました。
この記事には、その日の記録と、あとから足した決まりと、今も使っているシェルスクリプトの一部を書きます。
2026年10月12日時点の内容です。

## 起きた事

- 2026年9月28日 18:35、カーネルパニックで再起動しました。パニックの記録の文字列は `watchdog timeout: no checkins from watchdogd in 94 seconds` です。
- 直前は、Claude Code の3つのセッションと、Codex と、ブラウザの自動操作が同時に動いていました。
- 内蔵ストレージの空きは約5GBで、スワップは一杯でした。
- 21:21 に再ログインするまで、`launchd` で動かしていた毎時の投稿も止まりました。投稿は 21:22 に自動で再開し、止まっていた間の分は送っていません。

メモリが足りなくなると、macOS はディスクをスワップに使います。
空きが約5GBしか無かったので、スワップを増やす場所がありませんでした。

## 足した決まり

全社の決まりに、Mac の容量と負荷のファイルを1本足しました。
決まりの1番目は、次のとおりです。

> 重い作業は同時に1つまで

対象は、ブラウザの自動操作、動画の書き出し、大きなファイルの一括処理、サブエージェントの並列起動です。
始める前に、ほかのセッションが同じ種類の作業をしていないかを、共有の記録で見ます。

確かめ方は、決まりのファイルに3行で書いてあります。

```sh
df -h /                                        # 空き
sysctl vm.swapusage                            # スワップ
ps -Ao pid,%cpu,%mem,etime,comm -r | head      # 重い処理
```

## 数値の基準は、2回変えた

最初は、空き 20GB を基準にしました。
翌日の9月29日に、この固定の基準を外しました。
空きが数値を下回っているだけで、検査や制作を保留しないようにするためです。
外した後は、空きとスワップと応答を見て、重い処理を順番に進める形にしました。

10月11日に、止める線をもう一度決め直しました。
10月12日時点の線は、次の2つです。

- `memory_pressure` の空き率が 12% 未満
- 空きディスクが 6GB 未満

スワップの使用量では、判断しないことにしました。
使われなくなったページがスワップに残り、重い処理が終わった後も値が下がらなかったためです。
同じ日に、「同時に1つまで」に絞る対象も、Chrome の画面操作を使う仕事だけに変えました。

Codex に仕事を順番に送るスクリプトは、送る前にこの2つを見ます。
次は、実際のスクリプトから、変数の定義を省いて載せた物です（Mac の zsh 用）。

```sh
FREE=$(memory_pressure 2>/dev/null | awk -F': ' '/free percentage/{gsub("%","",$2);print $2}')
DISK=$(df -g / | tail -1 | awk '{print $4}')
if [ "${FREE:-100}" -lt 12 ] || [ "${DISK:-100}" -lt 6 ]; then
  echo "$(date '+%m/%d %H:%M') STOP mac free=$FREE% disk=${DISK}GB" >> "$LOG"
  exit 3
fi
```

`memory_pressure` は、最後の行に `System-wide memory free percentage: 31%` の形で空き率を出します。
`awk` で、その数字だけを取り出しています。

## 「Chrome の仕事は同時に1つ」を、印のファイルで守る

Codex に Chrome の画面操作を頼む仕事は、同時に1つまでにしています。
守り方は、印のファイルです。
依頼を送る時に `<依頼の名前>.chrome` という空のファイルを置き、Codex には、終わった時に `<依頼の名前>.done.md` を書かせます。

1件を送るスクリプト（`send_codex.sh`）の、混み具合を見る部分です。
実際のスクリプトから、変数の定義と、Chrome を使わない仕事の分岐を省いて載せています（Mac の zsh 用。`stat -f` は Mac の書き方です）。

```sh
# Chrome を使う作業は同時に1つ。
# 「印があり、完了の知らせが無く、記録が10分以内に動いている」作業があれば渡さない。
for M in "$DIR"/*.chrome(N); do
  B="${M%.chrome}"
  if [ ! -f "$B.done.md" ] && [ -f "$B.cli.out" ] \
     && [ $(( $(date +%s) - $(stat -f %m "$B.cli.out") )) -lt 600 ]; then
    echo "CODEX_BUSY: $(basename $B) が Chrome を使っている"; exit 2
  fi
done
: > "$DIR/$N.chrome"
```

`CODEX_BUSY` が返ったら、送る側は5分待ってから送り直します。
Chrome を使わない仕事（ファイルの読み書き、調べ物）には、印を付けません。
こちらは、Chrome の仕事と同時に動かしています。

## 列を組んだ後に起きた4つの失敗

10月11日から12日にかけて、画像づくりと記事の更新を、Codex へ順番に送る仕組み（以下、列）で続けて送りました。
その時に起きた事と、直した事です。

**1. 送信役のプロセスを止めても、仕事は止まらなかった。**
送る側の `node` のプロセスを `kill` しても、Codex の中では仕事が「実行中」のまま残りました。
残っている間は、次の画面操作が2分で返らなくなりました。
止める時は、Codex の側の一覧で仕事の ID を調べて、取り消しの命令を送るようにしました。

**2. `pgrep -f` で「動いているか」を見て、自分を数えた。**
列が動いているかを `pgrep -f "列の名前"` で見ていました。
待っている側のスクリプトの命令文にも同じ文字が入っていたので、`pgrep` が自分の待ち役を拾い、「動いている」と判定し続けました。
判定は、プロセスの名前を見るのをやめて、完了の知らせのファイルと、送信の台帳のファイルで見る形に替えました。

**3. バックグラウンドの待ち役が、知らせを出さずに消えた。**
`until` のループで完了を待つスクリプトを、バックグラウンドで動かしていました。
2時間ほどで、何も出さずに消えていました。
気づくまでの2時間20分、列は止まったままでした。
今は、1本終わるごとに知らせが来る形にして、30分たつと必ず知らせが来る見張りを併用する決まりにしています。

**4. 完了の知らせの直後に次を送って、仕事が重なった。**
Codex は、完了の知らせのファイルを書いた後に、最後の返答を書きます。
知らせを見てすぐ次を送ると、前の仕事がまだ終わっていない間に、2つ目が動き始めました。
知らせを見た後、前の仕事のプロセスが終わるのを待ってから、次を送るようにしました。

## スワップより先に、ディスクが尽きた

Chrome の仕事を12時間続けた時に、空きディスクが 15GB から 4GB まで減りました。
メモリの上位は、Codex のアプリと、その下の `codex` のプロセスでした。
スワップが増え続けて、ディスクの空きを先に使い切る形です。

空きを戻す時は、作り直せる物（`node_modules`、仮想環境、キャッシュ、公開済みの動画の中間ファイル）から外付けのディスクへ移しています。
AI には、消す操作をさせていません。
移した物の一覧と戻し方を残し、消すかどうかは私が決めます。
